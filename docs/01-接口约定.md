# 01 · 接口约定

展示端需要从后端拿到下面这些数据。**字段名对齐即可，不需要改前端渲染逻辑。**

---

## 一、作品对象

| 字段 | 类型 | 说明 | 前端怎么用 |
|---|---|---|---|
| `code` | string | **编码**（唯一标识） | 标题旁的等宽标签；同时作为点赞/评论的存储 key。**必须唯一且稳定** |
| `title` | string | 标题 | 卡片大标题（衬线体） |
| `author` | string \| null | 作者名 | 标题右侧，比标题小一档（20px → 13px）。**为空则不显示、也不占位** |
| `thumb` | string | 缩略图地址 | 卡片封面。建议 3:4 或 4:5 竖幅，宽 400~500px |
| `content` | string | **内容（HTML）** | **直接渲染**。格式约定见下文 ★ |
| `time` | string | 时间 | 元信息行；同时用于排序和年份筛选。建议 `YYYY-MM-DD` |
| `likes` | number | 点赞数 | 标题右侧计数（后端基准值，本机点赞在上面叠加） |
| `comments` | array | 评论区 | 见下文 |
| `audit` | object | 审核记录 | 只展示状态徽标，见下文 |

### 示例

```json
{
  "code": "DT-2026-001",
  "title": "秋夜寄友",
  "author": "江砚",
  "thumb": "images/art/qiuxing-thumb.webp",
  "time": "2026-09-12",
  "likes": 18,
  "content": "<p>寒灯独对夜三更，忽忆江头送客行。</p><blockquote>去岁秋杪，送友人于灞桥……</blockquote>",
  "comments": [
    { "user": "江砚", "text": "「一纸未成先有泪」这句最动人。", "at": "2026-09-13 10:22" }
  ],
  "audit": { "status": "approved", "reviewer": "社长", "at": "2026-09-12 20:05", "note": "" }
}
```

## 二、`content` 的 HTML 约定 ★ 最重要

### 1. 哪些标签承担什么语义

| 内容 | 用什么标签 | 展示端会怎么渲染 |
|---|---|---|
| **诗词正文** | `<p>` | 正常排（衬线体、行高 2） |
| **序 / 后记 / 自注** | **`<blockquote>`** | **左侧加一条朱砂色竖线**，颜色降一级、字号略小 |

**这条必须遵守。** 展示端**无法自动判断**哪段是诗、哪段是序——诗词长短句和散文在字符层面没有硬边界。所以只能靠录入端标记，展示端按标记加竖线。

> 也兼容 `<p class="note">`，但**推荐统一用 `<blockquote>`**，语义更清楚。

### 2. 标签白名单（安全）

`content` 是**直接插进页面**的 HTML。**这就是一个 XSS 攻击面。**

建议约定：

```
允许：p  br  strong  em  b  i  blockquote  h3  h4  ul  ol  li  img  figure  figcaption  a
禁止：script  iframe  style  object  embed  form  input  link  meta
属性：img 只允许 src / alt / title；a 只允许 href（且校验协议，禁 javascript:）
     任何 on* 事件属性（onclick / onerror …）一律禁止
```

**后端在存之前清洗一遍**（推荐），或者**展示端在渲染前清洗**。两边都做最稳。

> 若来源不完全可信而你又没做清洗，攻击者可以投稿一段带 `onerror` 的 `<img>`，**被攻击的是展示页**。

## 三、评论对象

| 字段 | 类型 | 说明 |
|---|---|---|
| `user` | string | 评论者名字（留空则前端显示「匿名」） |
| `text` | string | 内容，建议限制 200 字 |
| `at` | string | 时间，`YYYY-MM-DD HH:mm` |

排序：**新的在前**（前端会 `reverse()`）。

---

## 四、审核记录对象

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | string | `approved` / `pending` / `rejected` |
| `reviewer` | string | 审核人 |
| `at` | string | 审核时间 |
| `note` | string | 审核意见（可为空） |
| `log` | array | 完整流转日志 `[{ at, by, action }]`，**当前不公开显示** |

展示端只把 `status` 渲染成彩色徽标：

| status | 显示 | 颜色 |
|---|---|---|
| `approved` | 已通过审核 | 绿 |
| `pending` | 待审核 | 黄 |
| `rejected` | 未通过 | 朱砂红 |

> `log`（谁在什么时候提交、通过）属于内部流程，公开展示不太合适，所以数据里存着但没渲染。要展示随时可以加。

---

## 五、接口建议

前端目前是一次性拿到全部作品后在前端筛选/排序。数据量小的时候最省事，但**作品变多（几百篇）时要改成后端分页**。

建议的接口形态：

```
GET /api/works?year=2026&audit=approved&q=蜻蜓&sort=time&page=1&size=20
→ { total: 42, items: [ ...作品对象 ] }
```

**搜索范围**：标题 + 编码 + 正文（正文需去标签后比对）。

**排序**：`time`（最新发布） / `likes`（最多点赞） / `comments`（最多评论）。

**点赞与评论写入**：

```
POST /api/works/{code}/like      → 切换点赞，返回 { likes, liked }
POST /api/works/{code}/comments  → { user, text } → 返回新评论列表
```

前端要改的只有 `Store` 这一个对象（读写都走它），UI 逻辑不动。
